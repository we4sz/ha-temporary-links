# Full audit — 2026-07-02

Four parallel audit lenses (correctness/concurrency, security×2, product/UX, operations)
over the whole product, with the highest-severity findings independently re-verified against
the code. This is the input to the proposed epics/stories below; nothing here changes the
facit until adopted.

The facit currently maps 100% *of what it specifies* (71/71 ACs sound, 30 proven). The audit's
job was to find what the spec doesn't yet contemplate. It did — including one theme that
undermines a guarantee the product implies but does not actually keep.

## The load-bearing finding: the usage limit is advisory, not enforced

Three independent lenses (both security passes and the correctness pass) converged on this, and
it reproduces from a plain read of the code:

- The HA automation runs the link's real actions **unconditionally** as it fires the tracking
  event (`HomeAssistantService.cs:69-92`); it carries only the validity-window condition, never
  `MaxUses`.
- The add-on counts the use and deletes the automation only **afterward**, over a WebSocket
  round-trip (`LinkService.cs:192-286` driven by `HaEventListenerService.cs:139-173`).
- So `mode:single` blocks *concurrent* runs but not two POSTs milliseconds apart: a "single-use"
  door link can physically open many times while the count still reads 1/1 (correctness F1,
  security #1).
- It gets worse when the add-on is **down or disconnected**: HA still runs the actions, but the
  event is never received (`subscribe_events` has no replay), so the use is never counted, never
  audited, and the automation is **never deleted** — the "single-use" link stays live and
  reusable for its whole window (ops B2, correctness F4).
- Supporting cluster: no concurrency token on `TemporaryLink` (F2/m2), non-atomic HA↔DB writes
  on create/edit (F6/F7/m1), DB↔DB status races between the sweep and execution (F3), swallowed
  "database is locked" errors with no SQLite busy-timeout (F4/F9).

This is the origin of proposed **Epic E7 (Trustworthy enforcement)**.

## Product / UX gaps (net-new capability)

Recurring/scheduled access (weekday windows); operator notifications on use/failure/expiry;
recipient-facing success/failure feedback; sharing-mode transparency when there's no HA Cloud;
QR codes; group/multi-recipient send; search + pagination (audit hard-capped at 100, links list
unbounded); real operator attribution (every link is `CreatedBy="WebUI"` today); timezone
clarity and expiry countdowns; localisation (HA add-ons are multilingual); export. These become
proposed epics **E8 (recipient & notifications)**, **E10 (scheduling & reuse at scale)**, and
scattered stories.

## What is genuinely well-built (keep, don't regress)

Strong token entropy (~192 bits CSPRNG); robust confirm-page open-redirector guard (rejects
`hooks.nabu.casa.evil.com`, `@`-tricks, `javascript:`); fragment secrecy holds for a benign host
(no Referer leak); structured JSON serialisation everywhere → no injection (Jinja/JSON/SMS/log/
XSS all checked and clean); the home-side window condition as defense-in-depth; automation
cleanup on revoke/exhaustion/lazy-expiry/sweep with create-time compensation; order-preserving
DateTimeOffset storage; correct nullable-recipient handling; 33 green business-logic tests.

## Adversarial notes (things claimed but downgraded)

- Token lookup isn't constant-time, but no attacker-facing endpoint takes a token → not
  practically exploitable (security #8). Not proposing work.
- Truncating base64 of 32 random bytes to 32 chars does **not** weaken entropy below ~192 bits
  (it wastes ~8 bytes) — the earlier worry is a non-issue.
- Lingering automations are cosmetic *for the window guard* (HA still refuses outside the
  window) — but **not** cosmetic for `MaxUses`, which the automation never checks. That is
  exactly why E7.S1 matters.
